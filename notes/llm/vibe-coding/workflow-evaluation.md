# Workflow Evaluation For Maintainers

This file is not a project prompt. Do not paste it into a coding agent. Use it when changing Files 1–4.

Evaluate the exact committed workflow revision through a documented walkthrough, fixture, or automated test. Record the method, evidence, and result for every scenario; `Not applicable` is not a passing result. A later commit may record results for the immutable evaluated commit.

## Fixed Scenarios

| ID | Scenario | Pass condition |
| --- | --- | --- |
| E01 | New project with no repositories | File 2 gathers and proposes before mutation, creates the private lifecycle only with authority, and stops before product behavior. |
| E02 | Empty or partly initialized repositories | Existing material is classified and preserved; bootstrap changes only approved gaps. |
| E03 | Established project | Bootstrap records `retired-not-applicable` when memory exists and continues without rebuilding or claiming approval. |
| E04 | Active bootstrap in each active state | File 4 retrieves the exact recorded File 2, resumes the linked action, and prevents premature product work. |
| E05 | Retired bootstrap | File 4 never retrieves File 2 and begins ordinary continuation without repeating accepted questions. |
| E06 | Foundation revision changed | File 4 compares affected clauses, preserves established project contracts, and blocks only work governed by unresolved conflict. |
| E07 | Malformed lifecycle with one provable state | Evidence identifies one state; File 4 repairs only the lifecycle bookkeeping, logs it, and continues. |
| E08 | Lifecycle with ambiguous or missing approval | Repository contents are not treated as approval; affected mutation stops and requests only missing evidence. |
| E09 | Digest tool unavailable | No digest is invented; ordinary permitted reads disclose the gap, while File 3 grants no special publication authority. |
| E10 | Conditional rule with uncertain applicability | Observable router triggers load every clearly or possibly relevant section and the rule manifest explains the selection. |
| E11 | Documented checks without working enforcement | Bootstrap verification fails until the actual entry point, matrix, and required automated checks exist and run. |
| E12 | Large codebase map | Every tracked path retains a role; inventory maintenance and completeness are automated; ordinary work loads only summary and relevant entries. |
| E13 | Two concurrent sessions | Only one agent writes a branch and private memory; other mutation is isolated or stopped without losing either session's work. |
| E14 | Failed experimental work | The starting commit and pre-existing changes are known; only proven task-owned work is repaired or restored under authority. |
| E15 | Interrupted two-repository publication | The next session discovers both repository states and resumes the missing ordered step without reconstructing committed memory. |
| E16 | Closeout before the application repository exists | Expected absence is recorded from lifecycle state; closeout does not create the repository or report false failure. |
| E17 | Context becomes too large | The agent narrows retrieval or creates a truthful checkpoint; it does not silently omit required policy or invent compressed context. |
| E18 | Routine work and a complex work unit on one day | One daily file is used; routine tool activity creates no entry; each meaningful entry follows the four fields and 200-word cap. |

## Result Record

For each evaluated revision, append:

- exact commit and date;
- evaluator and method;
- one `Pass` or `Fail` result for E01–E18 with concise evidence;
- discovered regression or ambiguity;
- required follow-up.

Do not mark the workflow evaluated from general impressions or from a different revision.
